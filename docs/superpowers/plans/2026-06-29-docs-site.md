```adoc
`aptupdatechecker` accepts one optional subcommand.

`aptupdatechecker update`::
Updates the APT package cache. Requires root. Does not send notifications. Used by the system timer service.

`aptupdatechecker check`::
```

- [ ] **Step 1: Write how-it-works.adoc**

```adoc
= How it works

`aptupdatechecker` uses a privilege-separated architecture. Cache updates require root access, but desktop notifications must run inside your user session where D-Bus is available. The service splits these responsibilities across two systemd scopes.

== System scope (root)

A system timer runs `aptupdatechecker update` as root every 3 hours. This refreshes the APT package cache — equivalent to running `apt update`.

After a successful cache update, the service signals each active user session by creating the file `/run/user/<uid>/apt-updates-available` in each session directory under `/run/user/`.

== User scope (your session)

A path unit watches for `/run/user/<uid>/apt-updates-available`. When the system service creates that file, the path unit starts `aptupdatechecker check`.

`aptupdatechecker check` reads the existing APT cache (it does not update it), counts upgradable packages, and sends a desktop notification via D-Bus if any are found. It then removes the signal file.

A separate user timer runs `aptupdatechecker fwupd` roughly every 3 hours to check for firmware updates using `fwupdmgr`.

== Why two scopes?

A system service running as root cannot access your D-Bus session bus, so it cannot send desktop notifications to your desktop. Splitting the work means the cache update runs with the privileges it needs, and the notification runs with the session access it needs.

This also limits the impact of bugs: the notification code never runs as root.

== Notification requirements

Desktop notifications rely on a running notification daemon, such as `dunst`, `notify-osd`, or `mako`. Your desktop environment likely installs one automatically. If you see no notifications, check that a daemon is running.
```

```adoc
= Configuration

`aptupdatechecker` has no configuration file. You can change its behaviour by using systemd drop-in override files to adjust timer schedules.

== What you can change

* How often the APT cache updates (system timer — requires root to modify)
* How often the firmware check runs (user timer — modify as your own user)

You cannot change notification content or appearance through configuration.

== Changing the APT cache update frequency

The system timer runs every 3 hours by default. To change this, create a drop-in override:

[source,bash]
----
sudo systemctl edit aptupdatechecker_apt_cache_update.timer
----

`systemctl edit` opens a drop-in file in your editor. Add the following to change the interval to 6 hours:

[source,ini]
----
[Timer]
OnUnitActiveSec=6h
----

After saving, reload the daemon and restart the timer:

[source,bash]
----
sudo systemctl daemon-reload
sudo systemctl restart aptupdatechecker_apt_cache_update.timer
----

== Changing the firmware check frequency

The firmware update timer runs roughly every 3 hours with a small random delay. To change this for your user:

[source,bash]
----
systemctl --user edit aptupdatechecker_firmware_update_checker.timer
----

Add the following to change the interval to 6 hours:

[source,ini]
----
[Timer]
OnUnitActiveSec=6h
----

After saving, reload and restart:

[source,bash]
----
systemctl --user daemon-reload
systemctl --user restart aptupdatechecker_firmware_update_checker.timer
----

== Viewing active configuration

To see the effective configuration for a unit, including any drop-in overrides:

[source,bash]
----
systemctl cat aptupdatechecker_apt_cache_update.timer
systemctl --user cat aptupdatechecker_firmware_update_checker.timer
----

This shows the base unit file followed by any drop-in files that apply.
```

```adoc
= Troubleshooting

== No notifications appear

=== Check that a notification daemon is running

`aptupdatechecker` sends notifications via the freedesktop D-Bus notification interface. You need a notification daemon installed and running, such as `dunst`, `notify-osd`, or `mako`. Your desktop environment may provide one automatically.

If nothing appears, install or start your preferred notification daemon.

=== Check that D-Bus is accessible

[source,bash]
----
echo $DBUS_SESSION_BUS_ADDRESS
----

This should print a socket path. If it is empty, your user session may not have a D-Bus session bus running.

=== Check that user units are enabled and active

[source,bash]
----
systemctl --user status aptupdatechecker_apt_update_checker.path
systemctl --user status aptupdatechecker_firmware_update_checker.timer
----

Both should show `active`. If they show `inactive` or `failed`, enable them:

[source,bash]
----
systemctl --user enable --now aptupdatechecker_apt_update_checker.path
systemctl --user enable --now aptupdatechecker_firmware_update_checker.timer
----

== The APT check is not triggering

The APT update notification only runs after the system cache update completes. Check that the system timer is running:

[source,bash]
----
systemctl status aptupdatechecker_apt_cache_update.timer
----

If it shows `inactive` or `failed`, start it:

[source,bash]
----
sudo systemctl start aptupdatechecker_apt_cache_update.timer
----

The system service runs every 3 hours, starting 1 minute after boot. To trigger a run immediately for testing:

[source,bash]
----
sudo systemctl start aptupdatechecker_apt_cache_update.service
----

== Reading the logs

System service logs (APT cache update):

[source,bash]
----
journalctl -u aptupdatechecker_apt_cache_update.service
----

User service logs (APT check and firmware check):

[source,bash]
----
journalctl --user -u aptupdatechecker_apt_update_checker.service
journalctl --user -u aptupdatechecker_firmware_update_checker.service
----

To follow logs in real time, add the `-f` flag to any of those commands.

== The firmware check fails

`aptupdatechecker fwupd` requires `fwupdmgr` to be installed:

[source,bash]

which fwupdmgr
----

If it is not found, install `fwupd`:

[source,bash]
----
sudo apt install fwupd
----

If `fwupdmgr` is installed but the check still fails, check the user service log for the specific error message.
```

```adoc
= Architecture

== Privilege separation

`aptupdatechecker` splits its work across two systemd scopes to resolve a fundamental constraint: APT cache updates require root, but desktop notifications require access to your D-Bus user session.

A system service running as root cannot reach `DBUS_SESSION_BUS_ADDRESS`, so it cannot send notifications to the desktop. The solution is to run the cache update as root and signal the user session, which then runs the notification code under the user's own identity.

== System services (root)

These run under the system systemd instance:

`aptupdatechecker_apt_cache_update` (timer + service)::
Runs `aptupdatechecker update` every 3 hours. After a successful cache update, it touches `/run/user/<uid>/apt-updates-available` for each session directory found under `/run/user/`.

`aptupdatechecker_autoclean` (timer + service)::
Runs `apt autoclean` weekly.

`aptupdatechecker_autoremove` (timer + service)::
Runs `apt autoremove` weekly.

== User services (per-user session)

These run under each user's systemd instance:

`aptupdatechecker_apt_update_checker.path`::
Watches for `/run/user/<uid>/apt-updates-available`. When the file appears, it starts the corresponding `.service`, which runs `aptupdatechecker check`, sends a notification if updates are found, then removes the signal file.

`aptupdatechecker_firmware_update_checker` (timer + service)::
Runs `aptupdatechecker fwupd` on a timer (every ~3 hours, starting 10 minutes after session start, with a 2-minute random delay).

== Installed unit locations

[cols="1,2",options="header"]
|===
| Path | Contents

| `/lib/systemd/system/`
| System timers and services (root-level)

| `/usr/lib/systemd/user/`
| User path unit, timers, and services
|===

Unit source files live in `systemd/system/` and `systemd/user/` in the repository. `cargo-deb` reads these paths from `Cargo.toml` under `[package.metadata.deb]`.

== Signal file mechanism

The file `/run/user/<uid>/apt-updates-available` is the IPC channel between the system service and the user path unit. It exists briefly: the system service creates it, the path unit detects it and starts the check service, the check service removes it.

If this file persists (because the user units are not enabled), the path unit activates the check service the next time the user units start. Path units are edge-triggered on a file that already exists when they start.
```

```adoc
CI workflows run inside a Docker container (`tylerkelly13/rust-aptupdatechecker-ci:latest`) that has all build dependencies pre-installed. The Dockerfile lives at `.github/workflows/Dockerfile` and rebuilds automatically when changed on `main`.

|===
| Secret | Description

| Docker Hub username for pushing the CI image

| `DOCKERHUB_TOKEN`

== CI/CD workflows

The project uses reusable GitHub Actions workflows from the https://github.com/tylerkelly13/.github[tylerkelly13/.github] repository.

`check.yml`::
Runs on pull requests to `main` and `release/*` branches, and on manual dispatch. Calls `rust-run-checks` with coverage enabled. Ignores documentation and Dockerfile changes.

`bump.yml`::
Triggered manually from the Actions tab. Calls `rust-bump-version` to run CI, bump the version in `Cargo.toml`, and open a pull request.

`tag.yml`::
Fires when GitHub merges a pull request whose head branch starts with `bump-v`. Calls `rust-tag-on-merge` to push an annotated tag, which triggers `deploy.yml`.

`deploy.yml`::
Triggers on `v*` tag pushes. Runs `rust-run-checks`, then passes the build artifact to `rust-gh-release` to create a draft GitHub release.

== Debian packaging

`cargo-deb` reads packaging configuration from `Cargo.toml` under `[package.metadata.deb]`. It picks up systemd unit files from `systemd/system/` and `systemd/user/` as configured there.

The `debian/` directory contains maintainer scripts (`postinst`, `prerm`, `postrm`) that:

* Enable and start system timers after package installation (`postinst`)
* Stop system services before removal (`prerm`)
* Disable all units and reload the daemon on purge (`postrm`)

The system timer (`aptupdatechecker_apt_cache_update.timer`) enables automatically on install. Users must enable user units manually — see the xref:user:installation.adoc[Installation] page.
```

```adoc
= Module: main

`src/main.rs` is the binary entry point. It collects command-line arguments and dispatches to the appropriate module function.

== Dispatch

The dispatch is a `match` on the first command-line argument. There is no argument parser library — the subcommands are fixed strings with no flags, so a `match` on `args.get(1)` is sufficient.

[source,rust]
----
match args.get(1).map(|s| s.as_str()) {
    Some("update") => apt_update::update_cache_only(),
    Some("check")  => apt_update::check_only(),
    Some("apt")    => apt_update::update_and_check(),
    Some("fwupd")  => fw_update::update_and_check(),
    _              => { apt_update::update_and_check(); fw_update::update_and_check(); }
}
----

== Legacy behaviour

The default arm (no argument, or an unrecognised argument) runs both `update_and_check` and the firmware check. This is the original single-binary behaviour, preserved for backwards compatibility. The systemd units do not use this mode — they invoke specific subcommands.

== Coverage exclusion

`main()` carries `#[cfg(not(tarpaulin_include))]` to exclude it from coverage reports. It contains no logic to test; it only dispatches.
```

```adoc
= Module: common

`src/common.rs` provides the shared notification infrastructure used by both `apt_update` and `fw_update`.

== Design

All notification setup lives here so the two check modules do not duplicate it. The module exposes two public functions (`notify` and `notify_error`) and two enums (`NotificationType` and `App`) that callers use to express their intent. Internal details — icon names, urgency mapping, timeout value — are not exposed.

== Key types

`NotificationType`::
`Info` maps to normal urgency and the `info` icon. `Error` maps to critical urgency and the `error` icon.

`App`::
`Apt` sets the application name to `"Apt Update Checker"`. `Fwupd` sets it to `"Firmware Update Checker"`. This name appears in notification daemons that group notifications by application.

== Notification properties

All notifications share these fixed properties:

* Timeout: 30 seconds (30,000 milliseconds)
* Category hint: `system`
* Notification system: freedesktop D-Bus (`notify-rust` crate)

The category hint `system` tells notification daemons that these are system-level alerts, which may affect display priority.

== Public API

`notify(notification_type, app, title, body)`::
Builds and sends a notification. Prints to stderr if sending fails — it does not panic or return an error, because a failed notification is not a fatal condition.

`notify_error(app, title, message)`::
Convenience wrapper around `notify` with `NotificationType::Error`.

== Test coverage

`common.rs` has the most thorough test suite in the project — 13 unit tests covering icon and urgency mappings, appname uniqueness, timeout positivity, and notification construction. Tests use the private `build_notification` function to inspect the built struct without triggering a real D-Bus send.
```

```adoc
= Module: apt_update

`src/apt_update.rs` handles APT cache management, update detection, and notification dispatch for package updates.

== Entry points

The module exposes three public functions, each intended for a specific context:

`update_cache_only()`::
Runs as root. Updates the APT cache and signals active user sessions. Does not send notifications — it prints success to stdout or exits with code 1 on failure. Called by `aptupdatechecker update`.

`check_only()`::
Runs as user. Reads the existing APT cache and checks for upgradable packages. Skips the check if the cache is stale. Called by `aptupdatechecker check` (started by the path unit).

`update_and_check()`::
Legacy mode. Updates the cache then checks — requires both root access and D-Bus. Called by `aptupdatechecker apt` and the no-argument default.

== Cache freshness

`check_only()` guards against acting on a stale cache. It checks the modification time of `/var/cache/apt/pkgcache.bin`. If the file is older than 8 hours, the check is skipped with a message to stdout.

This prevents false "no updates" results from a cache the system service has not refreshed recently, such as after a long sleep or downtime.

== User session signalling

After a successful cache update, `update_cache_only()` calls `signal_user_sessions()`, which iterates `/run/user/` and creates `apt-updates-available` inside each subdirectory. Each subdirectory represents an active user session (named by UID).

Individual failures — for example, a stale session directory with wrong permissions — print to stderr and continue. The function does not abort because one session fails.

== Update counting

Package counting uses the `rust-apt` crate: `new_cache!()` macro followed by `PackageSort::default().upgradable()`. This is equivalent to what `apt list --upgradable` reports.

== Message formatting

`format_update_message(count)` handles the singular/plural distinction: "1 software upgrade available" vs "N software upgrades available". It is a public function so the test suite can verify it directly.

== Error handling

Errors at any step (cache initialisation, cache update, notification send) result in a desktop notification when running in user mode (`send_notifications = true`), or a stderr message when running in root mode. The module does not panic on runtime errors.
```

```adoc
= Module: fw_update

`src/fw_update.rs` checks for firmware updates using the `fwupdmgr` command-line tool from the `fwupd` project.

== Entry point

`update_and_check()` is the only public entry point. It refreshes the firmware metadata cache, then queries for available updates.

== fwupdmgr interaction

The module runs two `fwupdmgr` subprocesses:

`fwupdmgr refresh --force`::
Refreshes the firmware update metadata from LVFS (Linux Vendor Firmware Service). The `--force` flag bypasses the cooldown period that `fwupdmgr` normally enforces between refreshes. If this fails, the module sends an error notification and returns without checking for updates.

`fwupdmgr get-updates`::
Lists devices with available firmware updates. The module parses stdout to count updates.

== Output parsing

`fwupdmgr` does not provide machine-readable output (no JSON or structured format). The module counts `'Device ID: <word_chars>'` lines in stdout using a regex. Each match represents one device with an available update.

Exit code 2 from `fwupdmgr get-updates` means "no updates available" — this is a success case, not an error. The module handles codes 0 and 2 as success; any other code triggers an error notification.

== Panic on missing fwupdmgr

Both subprocess calls use `.expect(...)` rather than returning an error. This means the process panics if `fwupdmgr` is not installed or not in PATH. The assumption is that the Debian package installation ensures `fwupd` is present as a dependency.

== Public API surface

Two functions are public for testability:

`count_firmware_updates(output: &str) -> usize`::
Counts `'Device ID: ...'` pattern matches in a string. The test suite covers valid patterns, malformed input, mixed content, and edge cases.

`format_firmware_message(count: usize) -> String`::
Formats the notification body. Note: unlike `apt_update`, this function does not handle the singular case — "1 firmware updates are available" is a known inconsistency in the current implementation.
```
